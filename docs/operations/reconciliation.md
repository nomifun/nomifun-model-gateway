# 请求与支付对账

金额和 token 额度均使用整数。模型请求以 request_id 预扣并幂等结算；支付事件与入账在同一
事务中处理。运营方处理异常时必须保留这些身份边界，不靠直接修改用户余额或删除事件来重做。

## 模型请求

预扣是保守上界，最终收费仍按真实分项 usage 精确结算。缓存创建/读取或推理的更高单价会进入
金额上界；Responses 延续、有不透明 reasoning 历史或多模态输入时，可能使用模型声明的完整
context window 而不只计请求体字节。省略的原生输出上限会被明确约束，多个候选/图像也计入。
未使用部分在结算时释放。此策略可能在实际最终成本很低时先触发余额、额度或 TPM 不足；
没有可信 context 上界的请求会在发送前拒绝。运营方必须维护准确的模型能力/容量元数据，
不能把字节估计当作所有上游分词或隐藏注入内容的通用证明。

`reserved` 表示尚未最终结算的预扣；`settled` 和 `released` 为已完成状态；
`reconciliation` 表示上游可能已接受请求，但没有可完整结算的真实 usage 或存在定价/额度异常。
客户端断开、网络中断或流尾缺失不等于上游没有计费，因此不会自动把已接受请求免费释放。

1. 在管理员控制台打开 reservations，以 request_id 核对对应用户、模型、渠道、时间和预扣。
2. 从上游运营后台或其账务接口获取可核实的 usage。包含缓存创建、缓存读取、推理和图像数量等
   实际适用字段，不能用粗略 token 估算替代最终计量。
3. 有完整真实 usage 时选择 settle；上游确认未接受或未收费时才选择 release。
4. 必须填写原因。对账的账本/额度变更与管理员审计记录在同一事务中落库；重复完成不能再次收费。
5. 账本、用户余额、预扣余额、API key/套餐额度与供应商账单一起复核。无证据时保留 pending hold，
   向用户解释受影响额度和处理时限，不凭猜测结算。

后台 API 为 `POST /api/console/v1/admin/reservations/{request_id}/reconcile`，只允许管理员会话。
`action` 为 settle 或 release，`reason` 为必填，settle 必须包含已核实的 `usage`。
人工余额调整另有带审计和幂等键的管理入口，不能用它冒充某个模型请求的结算。

## 支付订单

支付默认禁用。启用前运营方填写自己的商户身份、签名/解密材料、HTTPS 回调与购买返回地址。
更换身份或凭据前必须对账未解决订单；不能把旧商户订单改挂到新商户。

对于 pending 订单，控制台对账会向官方支付接口查询，不接受浏览器支付成功页面作为入账证据。
回调或查询结果必须匹配订单、商户/应用、金额、币种和外部交易号；通过校验的事件幂等应用。
重复、迟到、无效签名或跨商户通知不能增加余额。保留原订单和外部交易关联用于退款及财务处理。

Stripe 与支付宝有相应测试/沙箱模式，真实模式必须由运营方自己完成验证；微信支付 v3 不声称
提供沙箱。本仓库的合成签名、加密回调与伪造 HTTP 服务测试不等同于微信真实商户交易验证，
也不等同于 Stripe/支付宝的真实测试环境交易。

当前没有自动定时对账守护进程或多实例调度承诺。运营方应明确 pending 订单和未知 usage 的
告警阈值、处理负责人、查询节奏和审计保存期限。批量查询入口仍应使用有权限的管理操作，
不得把人工和 webhook 入账逻辑分成两套账本。
